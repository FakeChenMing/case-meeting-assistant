# 会后交接模板（v1.1）

存放：本案“沟通记录-GPT/<session_id>/会后交接/<版本>/”。依次生成交接正文、事实与分析变更表、完整转写；原始事件和音频保持原样。

## 一、元数据与完整性

matter_id／session_id／会前包版本／会后包版本及 draft-ready 状态／参与人及角色（未核实名则标未知）／沟通起止时间与时区／设备与输入渠道／生成时间／转写最终事件序号／最后已分析序号／未处理范围。

| 文件类型 | 相对路径/分片ID | 时间范围 | 大小/校验摘要 | 可打开/可回听的实际检查 | 缺口 |
|---|---|---|---|---|---|
| 原始音频 |  |  |  | 未验证不得写已保存 |  |
| 转写原始事件 |  |  |  |  |  |
| 完整转写及更正记录 |  |  |  |  |  |
| 提示/用户处理记录 |  |  |  |  |  |

## 二、沟通结果摘要

本次解决了什么；仍未解决什么；哪些原判断需要改变；用户明确作了哪些决定。用户决定给出明确指令或原话依据；AI 建议不能混入决定。

## 三、事实与分析变更表（独立文件）

| 变更ID | 原事实/要件/争点ID及旧版本 | 新陈述或更正 | 状态及说话人核验情况 | 原话时间点/事件ID | 原材料对照 | 建议如何更新事实清单 | 对分析的影响及核验状态 |
|---|---|---|---|---|---|---|---|

分开列：新增陈述、转写纠正、对旧说法的实质改变、矛盾、补到的证据、待核分析。删除旧结论时保留其历史版本、原依据和变更原因；不能只保留新的平滑叙事。

## 四、问题闭环及点击记录

| 问题ID/issue_key | 为什么问/影响 | 已问时间 | 实际回答及出处 | 当前状态 | 用户动作与时间 | 是否仍缺证据 | 下一步 |
|---|---|---|---|---|---|---|---|

状态分别保留：候选、当前提示、已问待答、已解决、稍后再问、本次不问。已问不等于解决；本次不问不等于事实无关或已经核实。记录重大新证据导致的恢复建议及用户是否同意恢复。

## 五、补证、核验与任务

| 事项ID | 要取得/核验什么 | 对应事实及要件 | 由谁提供/处理 | 用户确认的期限（没有则写未定） | 来源 | 状态 |
|---|---|---|---|---|---|---|

## 六、法律分析及来源核验

按请求权基础逐项说明新增事实对成立要件、抗辩、责任或金额的影响。区分现场初步分析和会后完成核验的判断。沿用会前来源表格式，登记本次实际使用的法律 MCP、查询条件、日期、文号/条款/案号、交叉来源、冲突与失败；附本次技能实际调用记录。

## 七、会后处理端 接手行动

1. 核对会后包及关键附件并写独立回执。
2. 直接更新原事实清单和案件分析，沿用原格式，保留旧版、状态和来源；记录修改位置与变更ID。
3. 把尚缺材料或未核验结论保留为待核，继续必要法律检索。
4. **正式文书不得直接改写。**先提供拟修改文件、对应段落、修改理由和拟替换内容，取得用户确认后再修改。

| 正式文书 | 当前版本/段落 | 拟修改内容 | 依据及原因 | 是否已取得针对该修改的确认 |
|---|---|---|---|---|

## 八、接收回执与完成报告

接收端时间／包版本／实际下载检查／缺失项／事实清单已更新位置与版本／分析已更新位置与版本／尚待核验事项／待确认的正式文书变更。仅完成交接或下载不能写成案件更新已完成。

单机模式：上述角色均由同一台电脑分阶段执行；不要求同步或第二台设备。
